# 増設・撤去と保存型設定の実装記録

開始: 2026-09-08、更新: 2026-09-09。対象は一つのRootと常時給電機器の増設・撤去。
[全体設計](FIELD_NETWORK_EVOLUTION_2026-09-08.md)の一部を実装した記録であり、
親機交換・別現場への移設・電池の省電力運用の完成を意味しない。
OTAは対象外。GitHub Actions等は使わず、検証はローカルで行う。

2026-09-09の明示決定: Ninlilは汎用の通信基盤とし、KGuardを前提にしない。
USBで接続するホストとの境界は汎用APIとする。電池端末の起床・送信周期・受信窓は
利用アプリケーションの設定とし、センサー種類や業務判断をNinlilへ埋め込まない。
KGuardのMini PC常時接続と漏水センサーは利用例であり、全利用者への必須条件ではない。

## 現場でできるようにすること

対応firmwareを最初に一度書き込んだ後、USBから機器の識別情報と参加資格を設定する。
既存の全機器に新機器の個別公開鍵を書き直す必要はない。Rootが承認した資格を持つ
新機器は、常時給電の中継器を経由して発見・認証・参加できる。
同じ機器を同じ通信網へ戻す場合は保存した設定を使う。撤去で経路がなくなれば保留し、
別経路が利用可能になれば既存の経路選択と配送再開を行う。

機器を発見したこと、参加の許可、現在の参加確定、経路の利用可能性、相手の保存、
アプリケーション受領は別の結果。USB設定の成功だけで通信成功とは報告しない。
動的profileでは26バイトのCore受領通知を、既存のE2E認証済み制御通信kind 31で返す。
新しい逆方向DATA経路や時刻同期を通知だけのために要求せず、現在の参加状態と送受信者、
Coreの未完了契約を照合する。DATAとRelayの預かりACKはこの入口で拒否する。
通知が失われた場合は元のDATA再送と保存済み契約の重複照合から再通知する。
新しい預かり保存層は作らない。旧static profileは従来の経路付き通知を維持する。
kind 31を扱えない旧動的profileとの混在は未対応。切替前に全参加者を更新する。

## 実装した契約

- `ninlil_node_enroll`: 信頼できる管理操作で公開鍵・識別子・権限を追加し、使用前に保存する。
  同一要求は再実行可能。同じ機器の更新は参加世代が新しく、設置世代が後退しないことを要求する。
  別機器によるアドレス再使用、自機・Rootの差し替え、鍵の重複は拒否する。
- `ninlil_node_authorize` / `ninlil_node_admit`: Rootの署名で参加候補を認可する。
  秘密鍵は機器から出さず、既存のPSA実装でES256を処理する。
  署名の検証後も通常のEDHOC認証と永続Joinが必要。
  同じ資格の再発行でも、署名前に保存済みの参加台帳を再検証する。破損なら署名を発行せず停止する。
- `ninlil_node_advertise`: 自機の資格を通知し、未知の承認済み機器を発見する。
  電池Leafは中継しない。未知資格を無条件で取り次がず、署名を検証してから中継する。
- 参加情報の通知は受信先ごとに順番を進める。撤去済み機器への未応答によって、
  新設中継器に必要な端末情報が永久に後回しになる問題を修正した。
- 経路の準備・解除・適用通知では確認済みの相手を有界な走査で飛ばす。
  確認済みの相手を引くたびに次の2秒周期を空費する待ちをなくす。
  必要な全機器の確認、セッションの一致、経路の有効期限は省略しない。
- 動的profileの経路設定にはNP2を使う。準備期限と、Rootが確定してからの利用期限を
  分けることで、設定配布中に利用可能な時間を使い切る問題を扱う。両方とも最大60秒。
  準備期限を過ぎた初回適用は拒否し、確定済みの利用期限を再送で延長しない。
- PREPARE/APPLY受信を経路要求への応答として扱い、有効な準備・確認処理が進む間は
  同じ要求の送信を控える。期限切れや保存からの復帰では再要求する。中継の予約枠や
  暗号の検証を緩めず、低速モデルで受領通知まで確認した。
- `ninlil_setup`: 機器内にRoot、公開資格、設定版、自動起動を原子的に保存する。
  版番号を条件として更新し、最後の同一要求の再送を許容する。
  再送でも保存領域の破損を照合し、破損した設定を適用済みと返さない。

## 暗号・通信形式

公開機器レコードNM1は `NM 01`、非圧縮P-256公開鍵65バイト、既存NJ1のPENDING記録。
この用途のtransactionは `01` と15個のゼロに固定する。160〜224バイト。
これは公開設定であり、それ自体に署名や生存の証拠はない。

参加資格はRFC 9052のtagged COSE_Sign1。protectedは `{1: -7}`、unprotectedは空、
payloadはNM1、signatureはES256のRとS各32バイト。外部AADは空。
この一つの正規形式のみ受け付け、最大299バイト。
Root自身の公開鍵を明示的に固定する。独立した現場認証局や複数Rootの合意はまだない。
有効期限付き資格とは称さず、参加・設置世代と現行Joinの失効状態で制限する。

経路設定NP1は従来どおり。NP2は同じ98バイト長でversion byteを2とし、offset 40の
8バイトに準備期限を記録する。STAGEDでは両期限が一致し、COMMITTEDへの一度の遷移で
利用期限をRootの現在時刻+60秒に確定・保存する。以後の同一世代は期限が完全一致する必要がある。
参加者は初回COMMITTED受理が準備期限内であることと、残り利用時間が60秒以下であることを照合する。
既に適用を保存した参加者の再確認では、確定した同じ利用期限を使う。
Root再起動後の61秒待機、古い経路の解放、全参加者の生きたセッション証拠は維持する。
NP2の残り準備時間が「既存の時刻誤差上限+参加機器数×2秒」以下なら確定を控える。
その準備期限が切れてから再試行する。期限ぎりぎりの確定で更に60秒待つ状態を避ける。
NP2に未対応の旧機器は受理しないため、混在状態での動作を保証しない。動的profileへの切替前に全参加者を更新する。

発見フレームはNB1のkind 6。既存16バイトheaderに全長2、offset 2と最大220バイトを続ける。
一資格は最大2フレーム。組立1件・転送1件・自機1件を固定領域に保持する。
組立と転送の期限は30秒、署名検証の間隔は1秒以上、直近重複の抑制は10秒。
自機通知は参加前12〜15秒、参加後60〜63秒。最大4ホップ。通常優先度を使い、
重要通信・制御通信の予約枠を横取りしない。単一の組立枠による混雑時の遅れは残る。

独立したPython cryptography実装で作った公開COSE fixtureをCで検証する。
生成用秘密鍵は保存しない。切詰め、全バイト改変、別の署名者を拒否する試験を含む。

## 保存形式と移行

control journalに公開機器レコードtype 6を追加した。回収時にはJoin・経路より先に復元する。
静的rosterから移行するときは、旧機器の信頼情報と未完了の配送を既存の回収処理で保存してから切り替える。
実行中のノードへの設定差し替えは拒否する。

設定journalはRoot、任意の自機資格、最後のNCF1 sealからなる。sealは設定版・自動起動・
対象機器IDを含む。POSIXは原子的な置換、NORは既存の2バンク選択を利用する。
途中までの確定記録や誤った順序は破損として拒否する。

NI4のidentity記録は「配送保存領域を初期化済み、保存型設定が必須」を示す。
この印のある機器で設定が消えても、古いcompiled rosterへ戻ったり新規初期化したりしない。
機器IDと秘密鍵は維持する。**NI4/type 6使用後の旧firmwareへの無条件downgradeは不可**。

ESP32-S3の既存領域は移動せず、末尾へ以下だけ追加した。

| 領域 | 開始 | サイズ |
| --- | --- | --- |
| node_setup | 0x78a000 | 0x8000 |
| node_setup_gc | 0x792000 | 0xa000 |

終了は0x79c000で8 MiB Flash内。書込みツールは全旧保存領域と追加設定領域を前後のhashで照合する。
デバイスのバックアップや秘密鍵の読み出しはしない。

## USBでの設定

USB接続は信頼できる現地管理境界として扱う。ネットワークから無認証で同じ操作を公開しない。
無線の国・周波数・出力上限は検証したfirmware profileに固定し、管理ツールから勝手に変更しない。

```powershell
# 公開IDと設定の確認
python tools/node_hil/manage.py info --port COM3
# 既存3台の設定を保存型へ移す例（それぞれの実際のポートを使う）
python tools/node_hil/manage.py adopt --port COM3
python tools/node_hil/manage.py adopt --port COM5 --root-port COM3
python tools/node_hil/manage.py adopt --port COM7 --root-port COM3
# 新しい、未割当の機器への最初の設定
python tools/node_hil/manage.py provision --port COM9
python tools/node_hil/manage.py enroll --port COM9 --root-port COM3 --address 4 --role relay --autorun
```

新しい通信網のRootには、未割当機器で `root --address 1 --autorun` を使う。
`--authority`を省略した新規Rootではランダムな公開network IDを作る。
既存の通信網には `adopt` を使い、既存Rootへ新network IDを適用しない。
`enroll`で既存機器を更新するときは、Rootへ変更を書き込む前に機器側の設定を照合する。
未対応の役割・現場・アドレス変更や世代の後退を先に拒否し、Rootだけ更新されて既存機器が
参加できなくなる事態を防ぐ。`python tests/test_manage.py`で変更なしの拒否を確認する。
未設定機器のUSB状態はlocal/rootを0で返し、build時の仮番号で新規登録を誤って拒否しない。
`--autorun`を指定すると起動時に通信を開始する。省略時は保存後停止。
コンソールのXは自動起動を解除して停止する。Rはソフトウェア再起動。

Uプロトコル: start `00 op length:u16`、chunk `01 offset:u16 bytes`、execute `02`、
read `03 offset:u16`、status `04`、member `05 address:u16`。
opは設定1/Root署名2/資格検証追加3。連続chunkは最大120バイト、全upload最大534バイト。
設定payloadはexpected_revision:u64、autorun:u8、root_length:u16、Root NM1、自機資格。
応答には公開情報だけを含む。全外部入力に長さ・順序・版・識別子の照合を行う。
診断の `06 kind:u8` は受信数:u16、処理成功数:u16、最後の処理結果:i32を返す。
暗号検証後にownerへ渡った制御だけを数え、payloadや鍵は返さない。
カウンタは65535で飽和し、ownerの再起動で0になる。業務配送の証拠とは別である。

## 今回の試験と限界

### 再起動時の保持データと通信量

中継器が古い暗号セッションのデータを保持しているとき、新しいDATA経路の確定だけを
待つと、経路設定と保持データの回復が互いを待つ場合がある。自動回復は新経路に依存せず、
送信元に「Coreの保存状態が正常で、別の暗号セッションが確立済みか」を確認する。
この認証済みの証拠が返るまで、中継器は預かりデータを解放しない。

RECOVER_REQUESTは従来18バイトを受理し、末尾にrekey許可を付けた19バイトも受理する。
自動回復では末尾0を使い、同じセッションならBUSYのまま維持する。計画撤去では末尾1を使い、
従来どおり送信元へセッションの更新を要求できる。0/1以外は拒否する。
確認応答は従来の34バイト。新しい要求を送る全参加者には対応firmwareが必要。

回復要求は4秒以上、子機からの経路要求はノード全体で8秒以上の間隔を空ける。
PREPARE/APPLY受信済みの同じ経路については、その有効期限まで重複要求を抑制する。
親機は未確認の参加者を優先して経路設定を再送する。時刻同期の有効期限、暗号の照合、
配送の完了条件を緩めて通信量を削減する実装ではない。
確定済み経路の通知と、次の経路の準備は交互に進める。行きの通知ACKが失われても、
受領確認を返す経路を準備できる。単一の未確定proof領域は同時に別経路へ流用しない。
期限切れや別世代のEFFECTIVE通知は、現行経路の再確認要求を作らない。
生きた同じ経路で暗号の結び付きが不一致なら、通常の準備待ちを解除して再確認を要求する。
ESP送信待ちでは、同じ相手・優先度・内容の再送を一つにまとめる。自機で暗号化した
内容は現行sessionで両方を検証・比較する。中継中のopaque frameはバイト一致だけを扱う。
Core/Relayの保存データは解放しない。実送信後の再送は改めて受付し、TX直前の期限・
権限照合も維持する。比較は受信側のreplay状態を変更せず、秘密の平文を残さない。
制御通信の受付がBUSY/CAPACITYなら、その相手への次の暗号化・受付を500 ms待つ。
満杯の間にCoreの短いpoll周期で暗号番号だけを大量消費することを防ぎ、所有データは保持する。

中継するbootstrap/controlには最大240バイト・1件・2秒の揮発性待ち枠を設けた。
送信schedulerが一時的に満杯でも100 ms間隔で受付を再試行し、通常優先度のまま渡す。
現地ノード自身の制御用予約枠を消費せず、満杯時の別packetはCAPACITYを返す。
期限切れ・失効・再起動時はこの待ち枠を捨て、元の送信者が再試行する。
業務データを永続的に預かるRelay custodyとは別の一時転送である。
親機内だけで完了する保存・確認処理は、成功後に無線再送用の2秒待ちを入れない。
親機が送信待ちに入れたPREPARE/APPLY/EFFECTIVEは、実際の送信直前に現行の状態と照合する。
確定後の古い準備要求、確認完了後の不要な適用要求、期限切れ・撤回済みの経路、
既に確認応答を受けた相手への古い通知は送信しない。再確認が必要な現行APPLYは維持する。

前の時刻サンプルが30秒で失効しても、取得中の新しい時刻応答のchallengeは保持する。
旧サンプルからの時刻取得は引き続き失敗し、新しい認証済み応答が届いた場合だけ同期を回復する。
セッション喪失・時計の後退・明示的な無効化ではchallengeも破棄する。
同期要求は元の10秒の期限内で同じchallengeを2〜2.5秒間隔で再送する。期限は延ばさない。
失敗した窓の次の新規要求は窓の開始から30秒以降、成功時の更新は受信から15秒後とする。
認証・参加済みの相手機器との測定は、同期を待たずに開始する。観測結果のRootへの報告と、
経路確定・DATA配送には従来どおり有効な時刻が必要。Root再起動時の61秒の保護時間は維持する。

全3台の同時再起動試験では、受信先へ転送する前に中継器が暗号化データを保存したことを確認し、
親機の未完了記録と中継器の預かりを維持したまま再起動する。通常のファイル保存とNORモデルで、
重複適用なしに送信元のAPPLICATION_ACCEPTEDまで進める。低速モデルも180秒の既存制限を維持する。
待ち枠追加後も初期seed 3は期限超過し、親機内処理の待ち時間を修正した。
同じ条件でseed 1〜6と二つの保存方式の計12通りを再試験して全件合格した。
失敗したモデルと実機の記録も結果の分母から除外しない。

### 検証範囲

`enrollment_*`はRoot単独起動、動的登録、署名検証、回収・再起動、世代の後退拒否、
設定保存、破損後の重複応答拒否、設定消失時の停止を実Core/暗号と二つの保存backendで確認する。
`discovery_*`は親機と端末間の全フレームをモデルで遮断して資格の発見からJoinを試す。
`field_replacement_*`は5台モデルでB経由→B撤去後Aへ→A撤去で分断→未知Rの追加で保留配送を回復し、
その後の失効済みBの復帰を拒否する。代替経路の履歴と受領の重複を照合する。

3台実機の設定試験では、保存、同一要求の再送、異なる古い要求の拒否、再起動での自動起動、
公開ID維持、既存の受領履歴7件の維持を確認した。最初の試験器は停止中の未マウント台帳を
0件として比較してしまったため失敗。比較時に台帳を開くよう修正した再試験が合格した。
最初の直通遮断試験も中継器まで遮断したため取り下げ、成功証拠に含めない。

v10の保留受領回復は509.365秒で合格。v11の新規配送とv12〜v16の回復は期限内に完了せず、
同じIDを維持したv17の回復が196.588秒で合格した。次の新規1件も221.599秒で合格したが、
その次の3件試験は2件目の受領確定が570秒に間に合わず失敗。失敗は分母から除外しない。
v18は同じ保留IDの受領を365.161秒で回復し、履歴12件を維持。その後、再起動を挟まない
新規3件が570秒以内に全件受領確定し、履歴12→15件で重複適用なしを確認した。
各件の投入から受領確定の観測まで47.690/270.656/95.593秒。これは低遅延・長期安定性の合格ではない。
終了時にRelay預かりが4件残ったため、連続運転時の回収と容量も未解決として追跡する。
v19は未設定機器のUSB状態修正のみ。無線処理が同じでも、v18の実測をv19で再実行したとは称さない。
全試行と正確なhashは[結果記録](FIELD_RESULTS_2026-09-08.json)と[証拠の索引](evidence/2026-09-08-field/README.md)に残す。

実機の既存3台は以前の信頼情報を保持して移行するため、工場出荷状態の未知端末の登録試験とは区別する。
ソフトウェア受信遮断は建物や距離による物理的な圏外の証明ではない。
検証結果・コマンド・hashは併設の結果記録で固定する。

## 未完了の要件

- 信頼台帳は履歴込み最大16機器。静的profileの制約は維持するが、動的profileでは
  Coreの同時配送相手枠と信頼台帳を分ける。portは最大32個のcounter保存領域を用意する必要がある。
  MCU ownerは依然全16機器分のsession状態を確保する。16台の無線性能や電池向けRAM保証ではない。
- 失効したアドレスや機器履歴の自動再使用・無期限の増設は未実装。満杯なら新規受付を拒否し、既存履歴を消さない。
- 親機を**別の実物**へ交換する信頼・台帳・未配送データの引継ぎ、別現場への移設、既存機器の役割変更は未実装。
  reference firmwareは現在の保存領域を別networkへ使い回す設定を拒否する。同じ親機の再起動・再設置とは異なる。
- Battery Leafの役割と受信窓の基礎APIはあるが、MCUの睡眠・起床・再探索・電池測定を統合していない。
  `--role battery`は寿命や省電力動作の保証ではない。
- 4台以上の実機による代替中継、制御したFlash書込み中電源断、30回の反復、72時間運転、現場pilotは未実施。
- 混雑時の配送時間・台数・流量の保証は未確立。KGuard Core/表示盤/Cloudへの結合や
  物理表示の2秒受入は別製品の検証であり、汎用Ninlilの実装完了条件には含めない。

「一度書き込めば設置撤去できる」は、対応profileを設定した同じ通信網の承認済み機器についての目標。
現状の実装と証拠から、任意の親機交換や全現場での無設定運用まで完成したとは言えない。
