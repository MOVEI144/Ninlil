# Ninlil 開発再開メモ — 2026-09-07

## 目的

機器の追加・撤去・故障・通信環境の変化に対応し、安定性と配送時間を測って改善できる、製品非依存の通信OSSとしてNinlilを進める。
KGuardは利用製品の一つであり、Ninlilの実行・試験にKGuardのコード、業務DB、クラウドを必須にしない。

この文書は履歴・Issue・現在のソースを照合した再開計画である。Issue #14の提案全体を採用済みにするADR（設計判断記録）ではなく、実装や実機受入の完了証拠でもない。

## 最初の開発単位

### 1. W01：既存実装と追加設計の境界を確定する

成果物候補は`ADAPTIVE_NETWORK_CONTRACT.md`。以下を既存の[FOUNDATIONS](FOUNDATIONS.md)、[P0実装契約](P0_IMPLEMENTATION.md)、[運用profile契約](P0_OPERATIONAL_PROFILES_V1.md)との差分として記述する。

- 配送Core、通信全体の調整役（Coordinator）、参加・失効の許可元（Authority）、無線port、製品adapterの責任。
- 機器の識別、所属、認証session、経路、無線計画の世代を区別する。
- 起動中の経過時間、無線予定の時刻、再起動後も判断可能な期限を区別する。
- 最終宛先の保存証拠、途中の保管責任、Application受理、物理動作の結果を維持する。
- 通信量・集中発生・許容遅延などの要求と、容量不足時の明示的な受付拒否を定義する。
- API・Wire・Journal・Profileの互換性を個別に扱う。必要な形式変更は実装前に版と移行を決める。
- #4/#8の暗号処理、#5/#8のJoin処理の担当範囲と、制御通信の分割が必要になった場合の扱いを整理する。

完了条件：各判断に既存契約・Issueの根拠、採用範囲、後続へ残す判断、観測可能な試験条件があり、未実装機能を有効化しないこと。初回からW01〜W12全体の実装をまとめない。

### 2. W02の最初の範囲：既存Cコアで一対多を測れるようにする

最初は直接通信の固定構成とし、既存C実装をfake radio・clock・storageへ接続する。試験用に別の配送protocolを再実装しない。

- 1対1と親1台＋子4台の双方向通信を再現する。子4台は小規模な模擬試験の開始案であり、実機台数の確定ではない。
- 台数、通信量、payloadサイズ、無線設定、seed、損失、故障時刻、評価時間を入力として固定する。
- 単一無線の送受信同時不可、DATAと受領証の送信時間、有限queueを扱う。
- 1台の通信断、受領証欠落、重複、親の再起動、同時イベントを再現する。
- 受付数、拒否数、保存確認済み数、未完了数、端末ごとの待ち時間を出力する。成功分だけの遅延で良く見せない。

完了条件：同じ入力とseedで再現でき、1台の停止を他端末の成功や全体完了と取り違えず、再起動後も同じ論理messageの配送責任を保持すること。
これは固定方式の比較基準であり、Relay・自動最適化・実電波性能の受入ではない。

### 3. W04／M1：2台の実機で測定を始める

[M1受入手順](M1_HIL_ACCEPTANCE.md)を正本とし、[証拠テンプレート](M1_HIL_EVIDENCE_TEMPLATE.md)へ記録する。
Board A/Bの個体識別、配線revision、RF profile、firmware hashを固定し、無線初期化、各方向1000回の診断通信、各方向100件の永続配送、障害・再起動・USB再接続・電源断の順に証拠を積み上げる。
初期の通信成功だけでM1全体を完了にしない。

W01/W02の設計・模擬試験は物理受入前にも進められる。一方、実機一対多への拡張とRelay有効化は、それぞれ実装範囲と受入を別に切る。
